Planning for the start of a phase, run on the trunk after a merge. An issue tracker is flat, so a project that follows `set-foundation` keeps its order in a short `docs/ROADMAP.md`: a `Next` list of issue numbers in the order they get picked up, and an `Open questions` list of the open `question` issues. That list is a copy of tracker state, and it goes stale between phases. Issues close with the PRs that fixed them, new ones are opened on the way, and a question gets answered in passing. A stale `Next` is noticed when someone picks up a closed item. A stale `Open questions` never is.

The skill anchors on the roadmap's own last commit and gathers what changed since: issues opened, closed or relabelled, the commits the phase merged, and the `File these` list from the last `review-boundary` report, which survives in history after the report is deleted. It reconciles the lists against the whole tracker in both directions, and checks blockers in other repositories. A bundled script, `scripts/gather.sh`, does that gathering in one read-only pass and prints a compact digest, so the tokens go on the judgement rather than on raw tracker output. The mechanical fixes (closed items off, new questions on) are brought as obvious. The judgement is put to the author as a proposed order, with a reason for each placement: where the new work goes, and whether a deferred question has now been answered. It writes `ROADMAP.md` only once the order is agreed, and proposes, but never makes, changes to the tracker itself.
