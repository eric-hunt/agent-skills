Lays down a project's groundwork documents — architecture notes, invariants, contracts — and marks each rule `foundational`, `in question`, or a loose `contract`. **The deliverable is the tier, not the prose.** Most architecture documents fail the same way: a rule fought for over two days and a placeholder typed to stop thinking about it read identically on the page, so the next reader defends both with the same energy and the project pays complexity rent on decisions nobody actually made.

Two modes. On a new project it draws the rules from the author, caps them at five to eight, and marks almost all of them `in question` out loud, because they are predictions. On a running project it recovers the architecture the code already enforces — guards, assertions, tests — and reports the gap in both directions against whatever is written down: enforced but unstated, stated but unenforced, stated and contradicted. Every proposed rule carries a citation, so taste cannot launder itself into a foundation. On a mature codebase it expects the `foundational` share to run high — what survives years of refactoring was selected for being load-bearing — and records instead whether each rule is **armored**, so a violation nobody anticipated still goes red, or **vigilant**, defended only by tests of the cases someone thought of. The vigilant ones are where a real violation ships with every test green.

It also decides how many documents a project should have, splitting on evidence rather than up front, and writes the pointer lines into the always-loaded agent instruction file that send a reader to the right document at the right moment. Runs as a conversation; writes only once the author has been through the list.
